# CLAUDE.md

This file defines how Claude Code should behave when working inside this Obsidian Vault.

Before performing non-trivial work, read:

```text
AI_ENTRYPOINT.md
```

Then load task-specific context as needed.

---

# 1. Claude Code Role

Inside this Vault, Claude Code should act as both:

1. execution agent;
    
2. knowledge-aware collaborator.
    

It should not treat this repository purely as a code repository.

This repository may contain:

- Markdown knowledge
    
- Prompt assets
    
- project documentation
    
- experiments
    
- decisions
    
- workflows
    
- code-related notes
    

Preserve this structure.

---

# 2. Startup Behavior

When starting a task:

1. inspect the current working directory;
    
2. verify the Vault root;
    
3. read `AI_ENTRYPOINT.md`;
    
4. inspect relevant system protocols;
    
5. locate project context if applicable;
    
6. execute only after sufficient context is available.
    

Do not recursively read the entire Vault by default.

---

# 3. Project Detection

If the user references an existing project:

search under:

```text
04_Projects/
```

Read:

```text
00_CONTEXT.md
```

first.

Use that file to determine additional files to inspect.

If no matching project exists:

do not create one automatically unless creating a project is part of the request.

---

# 4. Planning

For substantial tasks, produce a short implementation plan before large edits.

The plan should focus on:

- objective;
    
- files affected;
    
- approach;
    
- validation.
    

Avoid excessively detailed plans for small changes.

---

# 5. Markdown Editing

When editing Markdown:

preserve:

- YAML frontmatter;
    
- internal links;
    
- headings;
    
- existing metadata;
    
- changelog history.
    

Do not convert existing formatting styles unnecessarily.

Do not rewrite an entire file when a targeted patch is sufficient.

---

# 6. Prompt Editing

When editing files under:

```text
03_Prompts/
```

follow:

```text
00_System/PROMPT_PROTOCOL.md
```

Before creating a Prompt:

search for similar existing prompts.

When modifying a Prompt:

update metadata when appropriate:

```yaml
version:
updated:
status:
quality_score:
```

Add meaningful changes to:

```text
Changelog
```

Do not increment the version for trivial typo-only changes unless the existing protocol requires it.

---

# 7. Code Work

If a project contains actual code:

before changing implementation:

1. inspect repository structure;
    
2. inspect relevant package/config files;
    
3. identify existing architecture;
    
4. avoid introducing unnecessary dependencies;
    
5. follow existing conventions.
    

After changes, run relevant validation such as:

```text
lint
typecheck
tests
build
```

when those scripts exist.

Do not claim validation succeeded unless it was actually run.

---

# 8. File Creation

Before creating a new file ask internally:

```text
Does this information belong in an existing file?
```

Prefer updating an existing canonical note over creating duplicates.

New files should have:

- meaningful names;
    
- clear ownership/domain;
    
- correct folder placement.
    

Avoid filenames such as:

```text
notes.md
test.md
temp.md
final.md
final2.md
```

unless they are intentionally temporary.

---

# 9. Knowledge Extraction

After significant implementation or research, check whether reusable knowledge emerged.

Examples:

- technical pitfall;
    
- reusable architecture pattern;
    
- Prompt pattern;
    
- workflow improvement;
    
- product insight.
    

If appropriate, suggest or create a distilled note under:

```text
02_Knowledge/
```

Do not automatically duplicate entire project notes.

---

record the experiment when useful.

Possible destinations:

---

# 12. Git Safety

Never perform destructive Git operations without explicit need.

Avoid:

```text
git reset --hard
git clean -fd
force push
history rewriting
```

unless explicitly requested and safe.

Before large changes, inspect:

```text
git status
```

if this Vault is Git-managed.

Do not commit or push unless instructed or established project workflow explicitly authorizes it.

---

# 13. Obsidian Safety

Do not alter `.obsidian` configuration casually.

Avoid introducing plugins unless specifically requested.

Prefer plain Markdown and native Obsidian links.

The knowledge architecture should remain usable even without third-party plugins.

---

# 14. External Information

Do not overwrite durable Vault knowledge with unverified external claims.

When research is used:

distinguish:

```text
Verified fact
Source-backed claim
Interpretation
Assumption
```

Preserve source links when available.

---

# 15. Completion Report

For substantial work, finish with a concise report:

```text
Completed
Changed files
Validation
Important decisions
Remaining issues
Suggested next step
```

Do not flood the user with low-level implementation details unless requested.

---

# 16. Claude-Specific Strengths

Claude may be especially useful for:

- long-context synthesis;
    
- codebase understanding;
    
- document restructuring;
    
- Prompt analysis;
    
- architectural reasoning.
    

Use these strengths selectively.

Do not over-analyze simple tasks.

---

# 17. Final Rule

Treat the Vault as persistent user infrastructure.

Optimize for:

```text
clarity
traceability
reusability
low duplication
future AI readability
```

Every edit should make the Vault easier, not harder, for both the user and future AI systems to understand.
