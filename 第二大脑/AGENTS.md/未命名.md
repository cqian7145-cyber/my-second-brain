# AGENTS.md

## Purpose

This file defines operational rules for AI coding agents and autonomous agents working inside this Vault.

Primary shared instructions are located in:

```text
AI_ENTRYPOINT.md
```

Read that file before substantial work.

---

# 1. Scope

These instructions apply to agents working on:

- code;
    
- project files;
    
- Prompt assets;
    
- documentation;
    
- experiments;
    
- workflows;
    
- knowledge notes.
    

The Vault should be treated as a persistent knowledge repository.

---

# 2. Instruction Priority

Use the following priority:

```text
User's current explicit request
>
Project-specific instructions
>
AI_ENTRYPOINT.md
>
AGENTS.md
>
System protocols
>
Existing conventions
>
Reasonable defaults
```

Never allow stale documentation to override an explicit current user instruction.

---

# 3. Context Loading

Do not recursively load the entire repository.

Use targeted retrieval.

For most meaningful tasks:

```text
AI_ENTRYPOINT.md
↓
Relevant system protocol
↓
Project 00_CONTEXT.md
↓
Relevant implementation/documentation
↓
Related decisions
```

Only expand context when required.

---

# 4. Before Editing

Before editing:

1. inspect existing files;
    
2. identify canonical source;
    
3. identify dependencies;
    
4. check whether similar content already exists;
    
5. choose minimum sufficient modification.
    

Do not create duplicate sources of truth.

---

# 5. Source of Truth

Prefer one canonical file for each concept.

Examples:

User context:

```text
00_System/USER_CONTEXT.md
```

AI behavior:

```text
00_System/AI_RULES.md
```

Current project context:

```text
04_Projects/<project>/00_CONTEXT.md
```

Prompt definition:

```text
03_Prompts/...
```

Long-term reusable knowledge:

```text
02_Knowledge/...
```

Do not copy the same information across many files unless references are insufficient.

Prefer links.

---

# 6. Editing Strategy

Prefer:

```text
small coherent changes
```

over:

```text
large uncontrolled rewrites
```

Preserve:

- YAML frontmatter;
    
- links;
    
- metadata;
    
- history;
    
- naming conventions.
    

Avoid formatting-only churn.

---

# 7. New Files

New files should only be created when they have a clear role.

Every new persistent file should answer:

```text
Why does this file need to exist?
Where is its canonical location?
Who or what will use it later?
```

Use descriptive names.

---

# 8. Prompt Assets

Files under:

```text
03_Prompts/
```

must be treated as versioned reusable assets.

Expected metadata may include:

```yaml
id:
name:
version:
status:
type:
category:
tasks:
models:
created:
updated:
quality_score:
tags:
```

Prompt lifecycle:

```text
draft
↓
testing
↓
production
↓
deprecated
```

Do not create near-identical Prompt variants without reason.

---

# 9. Project Work

When working on a project, keep its state current.

The project context should reflect:

```text
Goal
Current Status
Constraints
Decisions
Open Questions
Next Actions
Definition of Done
```

Do not let the implementation and project context diverge for major changes.

---

# 10. Coding Tasks

When code exists:

inspect before editing:

```text
README
package files
config
source structure
tests
existing conventions
```

Use the project's existing stack and architecture unless there is a clear reason to change.

Avoid unnecessary dependencies.

---

# 11. Validation

After code changes, run available checks where relevant:

```text
lint
typecheck
unit tests
integration tests
build
```

If a command fails:

report the failure accurately.

Never say:

```text
tests passed
```

unless tests were actually executed successfully.

---

# 12. Completion Criteria

A coding task is not complete merely because code was written.

Completion may require:

```text
implementation
+
validation
+
documentation update
+
project context update
```

depending on impact.

---

# 13. Decisions

When making a significant choice between competing approaches:

record the decision.

Examples:

- framework choice;
    
- database choice;
    
- API design;
    
- Prompt architecture;
    
- deployment approach;
    
- major scope change.
    

Avoid documenting trivial implementation decisions.

---

# 14. Experiments

Use experiments when uncertainty is empirical.

Examples:

```text
Prompt A vs Prompt B
architecture A vs architecture B
landing page variant
model comparison
retrieval strategy
```

Separate:

```text
hypothesis
test
result
decision
```

Do not retroactively rewrite a hypothesis after results are known.

---

# 15. Knowledge Capture

When a project teaches a reusable lesson:

distill it.

Do not simply copy project logs into Knowledge.

Transform:

```text
Specific experience
↓
General principle
↓
Reusable note
```

---

# 16. Destructive Actions

Do not:

- mass delete;
    
- overwrite unknown files;
    
- rewrite Git history;
    
- clear directories;
    
- rename large portions of the Vault;
    

without explicit authorization and a clear reason.

Preserve user data by default.

---

# 17. Archive

Old material should normally be archived rather than deleted.

Use:

```text
09_Archive/
```

or the relevant deprecated/completed location.

Traceability is valuable.

---

# 18. Git

When Git is available:

use:

```text
git status
git diff
```

to understand changes.

Do not automatically:

```text
commit
push
merge
rebase
force push
```

unless requested or explicitly established by the workflow.

---

# 19. Agent Communication

For substantial tasks, keep updates concise.

Communicate:

```text
what is being changed
important discovery
blocking issue
validation result
```

Do not narrate every command.

---

# 20. Final Response

After meaningful work, summarize:

```text
Result

Files changed

Validation

Important notes

Next recommended action
```

If there are no meaningful risks or next steps, do not invent them.

---

# 21. Core Principle

The goal is not merely to complete the immediate task.

The goal is to complete the task while preserving and improving the user's long-term system.

Optimize for:

```text
correctness
maintainability
traceability
context efficiency
reuse
AI readability
```
