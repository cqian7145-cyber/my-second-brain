扩展功能与隐私安全设计

这个插件的定位很清晰—— **本地优先的浏览历史智能管理器** 。基于你提供的 README，我从 **产品功能、技术架构、用户体验、隐私安全** 四个维度给出一些具体建议：

---

## 一、产品功能层面

### 1\. 分类引擎：从"规则维护"转向"用户可训练"

当前基于 `domain + keyword` 的规则匹配在初期有效，但维护成本高，且对中文内容支持可能不够精准。

**建议：**

- **允许用户自定义规则** ：在 Settings 里加一个"分类规则编辑器"，让用户自己添加域名/关键词到指定分类。这比写死代码更可持续。
- **引入轻量级本地 TF-IDF / 朴素贝叶斯** ：完全在本地根据用户的历史行为训练一个简单分类器（比如把用户手动修正的分类作为训练样本）。不需要云端 AI，也能实现"越用越准"。
- **支持多级分类** ：例如 `Programming > JavaScript` 或 `AI > LLM` ，而不是扁平的 10 个分类。

### 2\. 增加"浏览会话（Session）"概念

单纯的时间线列表不如"会话"有价值。用户经常是一段时间内围绕一个主题连续浏览多个页面。

**建议：**

- 按时间间隔（如 30 分钟无操作）自动划分会话
- 每个会话显示：起止时间、访问页面数、主要分类、可一键恢复（批量打开该会话所有页面）
- 支持手动合并/拆分会话

### 3\. 数据洞察：从"统计"到"洞察"

目前的 Dashboard 是描述性统计（今天访问了多少次），可以升级为诊断性/预测性洞察。

**建议：**

- **重复访问提醒** ："这是你本月第 15 次访问 Stack Overflow 的同一个问题，是否需要收藏？"
- **时间分布热力图** ：一周中哪些时段最高产/最容易分心
- **网站停留时长分析** ：不只是访问次数，结合 `chrome.tabs` API 或 `webNavigation` 估算实际停留时间（区分"打开即关闭"和"深度阅读"）
- **标签页僵尸检测** ：找出打开超过 24 小时但从未激活的标签页

### 4\. 收藏与笔记的增强

当前收藏是简单的 `{url: item}` 结构。

**建议：**

- **收藏夹支持文件夹/标签** ：而非单一列表
- **笔记支持 Markdown + 时间戳** ：记录"为什么收藏这个页面"
- **全文快照** ：使用 `chrome.pageCapture` 或 `chrome.downloads` 保存页面为 MHTML，防止链接失效后收藏变成"死链"

## 二、技术架构层面

### 1\. 存储层：从 chrome.storage.local 迁移到 IndexedDB

`chrome.storage.local` 有 **5MB 容量限制** ，且不适合复杂查询。对于重度用户，几个月的历史 + 笔记 + 快照很快就会触及上限。

**建议：**

- 使用 **IndexedDB** （通过 Dexie.js 等封装）存储历史记录和笔记
- `chrome.storage.local` 仅保留配置项（settings、用户偏好）
- 实现数据压缩：历史记录中 URL 重复度高，可以对域名做字典编码

### 2\. 性能：虚拟滚动 + 分页加载

如果用户有数万条历史记录，"Fast in-memory search" 在低端设备上会成为性能瓶颈。

**建议：**

- **虚拟滚动（Virtual Scrolling）** ：只渲染视口内的 DOM 节点
- **Web Worker 做搜索** ：把搜索逻辑放到 Worker 线程，避免阻塞 UI
- **增量索引** ：首次安装时只加载最近 1000 条，后台逐步建立完整索引

### 3\. 背景页（Service Worker）的利用

目前 `background.js` 只做了 side panel 设置，功能利用率低。

**建议：**

- **定时清理任务** ：每天凌晨 SW 唤醒，清理超过 N 天的历史缓存（用户可配置保留时长）
- **跨设备同步准备** ：虽然当前纯本地，但可预留 `chrome.storage.sync` 接口，让用户可选同步收藏夹和笔记（加密后同步）
- **快捷键监听** ：注册 `chrome.commands` 快捷键，如 `Ctrl+Shift+H` 快速打开 side panel

### 4\. 构建与发布流程

目前是直接加载 unpacked extension，缺少现代化构建。

**建议：**

- 引入 Vite/Rollup 打包，支持代码分割（side panel 和 background 共享 utils）
- 添加 ESLint + Prettier 保证代码质量
- 准备 Chrome Web Store 发布物料：1280x800 截图、宣传视频、隐私政策页面

## 三、用户体验层面

### 1\. 搜索体验升级

- **搜索高亮** ：结果中高亮匹配的关键词（标题和 URL）
- **搜索建议** ：输入时提示最近搜索过的关键词和常用域名
- **高级搜索语法** ：如 `category:AI after:2026-07-01 domain:github.com`

### 2\. 空状态与引导

- **首次安装引导** ：新用户打开后是一片空白（需要授权 history），应设计一个引导页说明权限用途和数据本地存储承诺
- **空状态插画** ：每个页面（Favorites/Notes/Summary）在无数据时给出行动建议

### 3\. 批量操作

目前看起来是单条操作（点星星、加笔记）。

**建议：**

- 支持多选（checkbox），批量：删除、修改分类、导出、添加到收藏夹
- 拖拽选择（类似 Gmail 的 shift 多选）

### 4\. 主题与可访问性

- 已支持 light/dark，建议增加 **跟随系统** 选项
- 确保颜色对比度符合 WCAG AA 标准
- 支持键盘导航（Tab 顺序、Enter 打开、Esc 关闭模态框）

---

## 四、隐私与安全层面

这是本地历史工具最敏感的部分，也是最大的信任资产。

### 1\. 数据加密

虽然数据存在本地，但如果电脑被他人使用或 Chrome 配置文件被复制，历史记录和笔记是明文可读的。

**建议：**

- 提供可选的 **密码保护/加密** ：使用用户设置的密码对 `notes` 和 `favorites` 做 AES 加密
- 锁屏机制：超过 N 分钟未操作 side panel，重新打开时需要输入密码

### 2\. 隐私模式与黑名单

- **自动排除 Incognito 历史** ：Chrome History API 本身不会返回隐私模式记录，但需明确告知用户
- **敏感网站黑名单** ：允许用户设置域名黑名单（如银行、公司内部系统），这些网站的历史既不显示也不存储
- **一键紧急清除** ：在 side panel 顶部加一个"紧急清除"按钮，立即清除插件内所有数据（比去 Chrome 设置里清除历史更快）

### 3\. 权限最小化

当前权限（history, storage, sidePanel）已经很克制。

**建议：**

- 在 manifest 中声明 `optional_permissions` ，如 `pageCapture` （保存快照）作为可选权限，用户需要时才申请
- 隐私政策页面明确声明："本扩展不会将任何数据上传至服务器，所有处理均在本地完成"

---

## 五、优先级建议

如果资源有限，建议按以下顺序迭代：

| 优先级 | 功能 | 原因 |
| --- | --- | --- |
| **P0** | IndexedDB 迁移 + 虚拟滚动 | 解决性能瓶颈，支撑重度用户 |
| **P1** | 用户自定义分类规则 + 搜索高亮 | 显著提升核心体验 |
| **P2** | 浏览会话 + 停留时长分析 | 差异化功能，从"历史查看器"升级为"浏览分析器" |
| **P3** | 数据加密 + 敏感网站黑名单 | 建立信任壁垒 |
| **P4** | 本地轻量 ML 分类器 | 技术亮点，但实现成本高 |

---

## 总结

HistoryMind 的核心价值主张很明确： **"你的浏览历史只属于你"** 。在这个基础上，建议不要只做一个"更好用的历史搜索框"，而是朝着 **"个人浏览行为的本地智能中枢"** 演进——让用户不仅能回顾过去，还能理解自己的上网模式、找回丢失的上下文、保护敏感足迹。

## 一、先回答核心问题：用户为什么愿意付费？

Google 历史管理的真实痛点不是"界面丑"，而是 **"搜不到"** 和 **"找不回"** ：

| Google 历史的局限 | 用户的真实痛苦 | 付费意愿 |
| --- | --- | --- |
| 只索引 URL + 标题，不索引页面正文 | "我记得那篇文章讲了 Redis 限流，但标题是《第七章：性能》" | ⭐⭐⭐⭐⭐ |
| 90 天左右自动清理旧记录 | "三个月前看到的一个方案，现在找不到了" | ⭐⭐⭐⭐⭐ |
| 简单子串匹配，无语义理解 | "我记得是关于认证流程的，但想不起具体关键词" | ⭐⭐⭐⭐ |
| 无页面快照，链接失效即永久丢失 | "收藏的页面 404 了，内容再也看不到了" | ⭐⭐⭐⭐⭐ |
| 无跨设备加密同步 | "公司电脑查到的资料，回家想继续看找不到" | ⭐⭐⭐⭐ |
| 无行为分析 | "我每天到底花多少时间在刷短视频？" | ⭐⭐⭐ |

**付费价值主张应该是：**

> **"HistoryMind 是你浏览过的整个互联网的本地搜索引擎 + 时光机。Google 历史帮你回忆网址，HistoryMind 帮你找回知识。"**

## 二、必须添加的付费功能（按优先级排序）

### 🔴 P0：全文索引 + 语义搜索（核心壁垒）

这是 **最大差异化** ，也是 TraceMind、Retrospective History 等竞品的付费锚点。

- **全文索引** ：自动索引每个访问页面的正文内容（通过 `chrome.pageCapture` 或内容脚本提取文本），建立本地倒排索引
- **语义搜索** ：使用本地轻量嵌入模型（如 `transformers.js` 的 all-MiniLM），支持"我记得是关于 OAuth2 安全漏洞的"这类模糊查询
- **高亮预览** ：搜索结果直接显示匹配片段在正文中的位置

> 这是从"电话簿"到"搜索引擎"的跨越，用户一旦用过就回不去。

### 🔴 P0：页面快照 + 离线查看器（防止知识丢失）

- **自动保存页面快照** ：访问页面时后台保存为 MHTML 或精简 HTML
- **离线查看器** ：即使原站 404、付费墙、或内容被删除，仍可在插件内完整查看
- **截图存档** ：低分辨率免费，高清/完整截图 Pro 专属（TraceMind 已验证此模式）

### 🔴 P1：无限历史保留 + 智能清理（对抗 Chrome 的 90 天限制）

- Chrome 历史约 90 天后会被清理，HistoryMind 可 **永久保留** 自己的索引和快照
- 免费版保留 90 天，Pro 版无限期
- 智能清理：自动归档低频页面，保留高频/收藏/有笔记的页面

### 🔴 P1：跨设备加密同步

- 使用用户密码对数据做端到端加密，通过 `chrome.storage.sync` 或自建加密同步服务
- 免费版仅限单设备，Pro 版支持多设备同步
- **关键** ：必须在本地解密，服务器只存加密 blob

### 🟡 P2：生产力分析 + 行为洞察（RescueTime 模式）

- **时间分布热力图** ：一周中哪些时段最高产
- **网站停留时长** ：区分"打开即关闭"和"深度阅读"
- **分心指数** ：识别并统计高频切换、无意义滚动
- **周/月报告** ：自动生成"你的浏览行为报告"

### 🟡 P2：AI 自动标签 + 智能分类

- 用本地 LLM（如 `chrome.aiOriginTrial` 或 transformers.js）自动提取页面关键词、生成摘要
- 智能分类不是基于死规则，而是基于内容理解
- 支持用户训练：用户手动修正分类后，本地模型学习偏好

### 🟡 P3：会话恢复 + 上下文重建

- **自动会话分组** ：按时间间隔（30 分钟无操作）划分浏览会话
- **一键恢复会话** ：批量打开某次会话的所有页面
- **上下文线索** ：显示"你在访问这个页面前后还看了什么"

## 三、应该删除或弱化的功能（做减法）

当前 README 中的一些功能 **价值感不够强** ，甚至会稀释付费感知：

### ❌ 建议删除/大幅弱化：

| 功能 | 问题 | 建议 |
| --- | --- | --- |
| **Rule-based 分类** | 维护成本高、准确率有限、用户感知弱 | 保留为基础功能，但不要用"Smart Categorization"作为卖点。付费版用 AI 语义分类替代 |
| **Daily Summary（当前版本）** | 如果只是"今天访问了 12 个 AI 网站"，价值感极低 | 要么升级为 **AI 生成的洞察报告** （"本周你在深度学习领域投入了 8 小时，推荐阅读..."），要么删掉 |
| **Favorites（简单星标）** | Chrome 自带书签已覆盖此需求 | 升级为 **智能收藏夹** （支持文件夹、标签、全文笔记、自动打标签），否则不要作为独立页面 |
| **Notes（简单文本）** | 太基础，与分类、收藏割裂 | 升级为 **页面批注系统** （高亮正文 + 边注 + Markdown），与快照联动 |
| **主题切换（Light/Dark）** | 基础功能，不应占用开发资源 | 保留但不做为功能亮点 |

### ⚠️ 建议重新设计：

| 功能 | 当前形态 | 建议升级 |
| --- | --- | --- |
| **Dashboard** | 统计数字堆砌 | 改为 **"本周洞察"** ：不只展示数字，而是给出可行动的结论（"你在 StackOverflow 的同一个问题上停留了 4 次，需要收藏吗？"） |
| **Export/Import JSON** | 极客功能 | 改为 **加密备份到本地文件/云盘** （Pro 专属），普通用户不会手动导 JSON |

## 三、必须添加的 Pro 付费功能（按优先级）

### 🔴 P0：全文索引 + 语义/自然语言搜索（核心壁垒）

- **语义搜索** ：使用本地轻量嵌入模型（如 `transformers.js` 的 all-MiniLM），支持"我上周看过的那个 MCP 教程"这类模糊查询

- **Command Palette** ：输入 `>` 执行命令（Export / Dark Mode / Refresh / Today's Summary）
- **高亮预览** ：搜索结果直接显示匹配片段在正文中的位置

> 参考：TraceMind、Retrospective History 均以此作为付费锚点。

### 🔴 P0：页面快照 + 离线查看器（防止知识丢失）

- **自动保存页面快照** ：访问页面时后台保存为 MHTML 或精简 HTML
- **离线查看器** ：即使原站 404、付费墙、内容被删除，仍可在插件内完整查看
- **截图存档** ：低分辨率免费，高清/完整截图 Pro 专属

### 🔴 P0：无限历史保留 + 智能清理（对抗 Chrome 90 天限制）

- Chrome 历史约 90 天后自动清理，HistoryMind Pro **永久保留** 自己的索引和快照
- 智能清理策略：自动归档低频页面，保留高频/收藏/有笔记/有快照的页面
- 用户可配置保留时长和存储上限

### 🔴 P1：跨设备端到端加密同步

- 使用用户密码对数据做 AES 加密，服务器只存加密 blob，本地解密
- 免费版仅限单设备；Pro 版支持多设备同步
- 可选同步范围：全部数据 或 仅收藏/笔记

### 🔴 P1：Workspace 工作区（一键恢复研究上下文）

- 保存一组相关网页为一个 Workspace（如"Chrome 插件学习"包含 18 个页面）
- 支持一键恢复：批量打开 Workspace 内所有页面

- 未来可扩展为 Notion / Obsidian 集成导出

### 🟡 P2：Timeline 时间线视图 + 会话恢复

- **Timeline 视图** ：不是"Today: 145 Records"，而是 09:00 ChatGPT → 09:12 GitHub → 09:40 Chrome Docs 的纵向时间轴
- **自动会话分组** ：按时间间隔（30 分钟无操作）划分浏览会话
- **一键恢复会话** ：批量打开某次会话的所有页面
- **上下文线索** ：显示"你在访问这个页面前后还看了什么"

### 🟡 P2：Knowledge View / 知识图谱（第二大脑）

- 自动聚合相关页面：Chrome Extension → GitHub → YouTube → Official Docs → Blog
- 可视化知识网络：页面之间的跳转关系、共同主题聚类
- AI 自动总结：基于聚合内容生成主题摘要

### 🟡 P2：AI 能力统一接口 + 本地 AI 功能

- **AI Provider 接口** ：统一封装 `summarize()` / `classify()` / `search()` / `tag()` / `embedding()` ，未来可接入 Gemini / Claude / OpenAI / Ollama

### 🟡 P2：生产力分析 + 行为洞察

- **时间分布热力图** ：一周中哪些时段最高产

## 一、最让我受启发的三个底层洞察

### 1\. "按场景重组，而非按时间"——产品架构的范式转换

文档开头提出的这个框架是最核心的启发。Chrome 自带历史按时间排序，本质上是 **机器视角** （什么时候发生了什么事）；而用户的大脑是按 **任务/意图/场景** 来组织记忆的。

这意味着 HistoryMind 的底层数据结构不应该是一张扁平的 `(url, title, timestamp)` 表，而应该是一张 **有向图** ：

- 节点：页面
- 边：跳转关系、主题相似度、同一会话关联
- 聚类：任务/项目/工作区

当数据结构变成图之后，"研究路径图谱"、"跳转链路拆解"、"知识图谱"这些功能就不是"附加功能"，而是 **同一套底层能力的不同可视化** 。

### 2\. "自动遗忘与归档"——反直觉但关键的设计

文档最后提到的"超过30天未点开的链接自动压缩为归档包"是一个被严重低估的思路。大多数工具都在追求"保存一切"，但这会带来两个问题：

- **性能焦虑** ：数据量膨胀导致搜索变慢、存储占满
- **认知负担** ：用户面对"30000条历史"会产生无力感

**智能遗忘比无限保存更难，也更有价值。** 它的逻辑应该是：

- 高频访问 + 有笔记/高亮/收藏 → 完整保留 + 优先索引
- 中频访问 + 无互动 → 保留摘要 + 快照
- 低频访问 + 无互动 → 压缩为 `(title, domain, date)` 的归档包
- 敏感域名（银行/内网）→ 根据用户设置直接排除

这解决了之前讨论的 IndexedDB 性能问题—— **不是把所有数据都塞进高速索引，而是分层存储。**

### 3\. "关系发现"比"信息存储"更有价值

文档中多个身份的需求本质上是同一个底层能力： **发现页面之间的关系** 。

- 科研人员的"研究路径图谱" → 发现跳转关系
- Affiliate 的"跳转链路拆解" → 发现重定向关系
- HR 的"候选人看板聚合" → 发现同一实体的多页面关联
- 设计师的"色板提取" → 发现视觉相似性

这启发我：HistoryMind 的核心竞争力不应该是"我存了多少条历史"，而是 **"我能发现用户自己都没意识到的浏览模式"** 。

| **导出** | 一键导出高亮 + 笔记到 Notion / Obsidian / Markdown |

### 一个更激进的想法："高亮"作为付费墙的核心

## 一、文本定位与容错恢复算法

现代网页是活的——A/B 测试、懒加载、广告替换、SPA 路由切换，都会导致 DOM 结构变化。我们需要一套 **多层级的定位策略** ，从精确到模糊逐步降级。

### 1.1 四层定位策略

```markdown
L1: 精确路径定位（XPath + 文本偏移）
    ↓ 失败
L2: CSS 选择器 + 文本指纹
    ↓ 失败
L3: 段落语义相似度匹配（Levenshtein + TF-IDF）
    ↓ 失败
L4: 快照坐标叠加（兜底方案）
```

#### L1：精确路径定位（首次高亮时记录）

```javascript
// 记录高亮时的精确位置
function serializeRange(range) {
  return {
    // DOM 路径
    startPath: getXPath(range.startContainer),
    startOffset: range.startOffset,
    endPath: getXPath(range.endContainer),
    endOffset: range.endOffset,
    
    // 文本内容（用于校验）
    text: range.toString().trim(),
    contextBefore: getTextBefore(range, 50),
    contextAfter: getTextAfter(range, 50),
    
    // 页面元数据（用于识别页面版本）
    url: location.href,
    title: document.title,
    timestamp: Date.now()
  };
}

// XPath 生成器（考虑 Shadow DOM 和 iframe）
function getXPath(node) {
  if (node.id) return \`//*[@id="${node.id}"]\`;
  
  const parts = [];
  while (node && node.nodeType === Node.ELEMENT_NODE) {
    let index = 1;
    let sibling = node.previousSibling;
    while (sibling) {
      if (sibling.nodeType === Node.ELEMENT_NODE && sibling.tagName === node.tagName) {
        index++;
      }
      sibling = sibling.previousSibling;
    }
    const tag = node.tagName.toLowerCase();
    parts.unshift(index > 1 ? \`${tag}[${index}]\` : tag);
    node = node.parentNode;
  }
  return '/' + parts.join('/');
}
```

**L1 的局限** ：页面结构 slightest 变化（加一个 `<div>` ）就会导致 XPath 失效。所以 L1 只作为 **首选尝试** ，必须配合 L2-L4 做容错。

---

#### L2：CSS 选择器 + 文本指纹（结构微变时恢复）

当 XPath 失效时，尝试用 **语义化的 CSS 选择器** + **文本指纹** 重定位：

```javascript
function tryRecoverWithSelector(highlight) {
  // 1. 尝试用 class + 标签构建更鲁棒的选择器
  const candidates = document.querySelectorAll(
    \`p, article, section, div[class*="content"], div[class*="article"]\`
  );
  
  // 2. 文本指纹匹配（前后上下文 + 自身文本）
  for (const node of candidates) {
    const text = node.textContent.trim();
    if (fuzzyMatch(text, highlight.text, highlight.contextBefore)) {
      // 在节点内重新计算偏移量
      const newRange = findSubRange(node, highlight.text);
      if (newRange) return newRange;
    }
  }
  return null;
}

// 文本指纹匹配：编辑距离 + 子串匹配
function fuzzyMatch(haystack, needle, context) {
  // 直接包含
  if (haystack.includes(needle)) return true;
  
  // 编辑距离（允许 15% 的字符变化）
  const distance = levenshteinDistance(
    haystack.slice(0, needle.length * 2), 
    needle + context
  );
  return distance / needle.length < 0.15;
}
```

---

#### L3：段落语义相似度（内容大改版时恢复）

如果页面做了大幅改版（比如 Medium 文章重构），L2 也会失效。此时需要 **段落级别的语义匹配** ：

```javascript
async function tryRecoverWithSemantic(highlight) {
  // 1. 提取当前页面所有文本块
  const textBlocks = extractTextBlocks(document.body);
  
  // 2. 计算每个文本块与目标高亮的相似度
  // 方案 A：基于 TF-IDF + 余弦相似度（纯本地，无依赖）
  const targetTokens = tokenize(highlight.text + highlight.contextBefore);
  
  let bestMatch = null;
  let bestScore = 0;
  
  for (const block of textBlocks) {
    const blockTokens = tokenize(block.text);
    const similarity = cosineSimilarity(targetTokens, blockTokens);
    if (similarity > bestScore && similarity > 0.7) { // 阈值 0.7
      bestScore = similarity;
      bestMatch = block;
    }
  }
  
  // 方案 B：使用本地 Embedding 模型（更精准，但有计算成本）
  // const targetEmbedding = await localEmbed(highlight.text);
  // ... 与所有 block 的 embedding 做余弦相似度
  
  if (bestMatch) {
    return findSubRange(bestMatch.node, highlight.text);
  }
  return null;
}
```

**关键设计** ：L3 是 **异步的** 且 **计算密集型** ，应该：

- 在 Web Worker 中执行
- 只在用户主动打开高亮侧边栏时触发，而非页面加载时
- 如果 500ms 内未找到匹配，直接降级到 L4

#### L4：快照坐标叠加（终极兜底）

## 三、渲染性能与工程边界

### 3.1 大量高亮的性能策略

假设用户在长文（如 2 万字的技术文档）上做了 50 处高亮：

**问题** ：每次页面滚动/重排时，50 个 `<span class="highlight">` 可能导致重绘性能问题。

**解决方案** ：

```javascript
class HighlightRenderer {
  constructor() {
    this.highlights = [];
    this.visibleHighlights = new Set();
    this.observer = new IntersectionObserver(
      entries => this.handleVisibilityChange(entries),
      { rootMargin: '200px' } // 预渲染视口上下 200px
    );
  }
  
  render(highlights) {
    // 1. 分批渲染，避免阻塞主线程
    const chunks = chunk(highlights, 5); // 每批 5 个
    
    chunks.forEach((chunk, index) => {
      requestIdleCallback(() => {
        chunk.forEach(h => this.renderSingle(h));
      }, { timeout: 100 });
    });
  }
  
  renderSingle(highlight) {
    // 2. 使用 CSS Containment 减少重排影响
    const span = document.createElement('span');
    span.className = \`hm-highlight hm-highlight-${highlight.color}\`;
    span.style.contain = 'layout style paint';
    span.dataset.highlightId = highlight.id;
    
    // 3. 事件委托，避免每个高亮绑定监听器
    span.addEventListener('mouseenter', this.onHighlightHover);
    span.addEventListener('click', this.onHighlightClick);
    
    // 4. 插入到 Range
    try {
      const range = this.recoverRange(highlight);
      range.surroundContents(span);
      this.observer.observe(span);
    } catch (e) {
      // 跨元素高亮（Range 跨多个 block）时 surroundContents 会失败
      // 改用多个 span 包裹
      this.renderMultiSpan(highlight, range);
    }
  }
}
```

### 3.2 跨域与 CSP 限制

**问题** ：很多网站有严格的 `Content-Security-Policy` ，禁止内联脚本和样式注入。

**解决方案** ：

- 使用 `chrome.scripting.executeScript` 注入内容脚本，而非内联 `<script>`
- 高亮样式通过 **外部 CSS 文件** 注入（ `css: ["styles/highlights.css"]` in manifest）
- 对于极端 CSP 的网站（如 GitHub），使用 **Shadow DOM 隔离样式** ：

```javascript
function injectHighlightStyles() {
  const style = document.createElement('style');
  style.textContent = \`
    .hm-highlight {
      background-color: rgba(255, 235, 59, 0.4);
      border-bottom: 2px solid #ffc107;
      cursor: pointer;
      transition: background-color 0.2s;
    }
    .hm-highlight:hover {
      background-color: rgba(255, 235, 59, 0.7);
    }
    .hm-highlight-note::after {
      content: '📝';
      margin-left: 4px;
      font-size: 0.8em;
    }
  \`;
  
  // 使用 Shadow DOM 或文档根注入
  if (document.adoptedStyleSheets) {
    const sheet = new CSSStyleSheet();
    sheet.replaceSync(style.textContent);
    document.adoptedStyleSheets = [...document.adoptedStyleSheets, sheet];
  } else {
    document.head.appendChild(style);
  }
}
```

### 3.3 内容脚本的权限设计

在 `manifest.json` 中，高亮功能应该作为 **可选权限** ：

```json
{
  "permissions": ["storage", "history", "sidePanel"],
  "optional_permissions": ["activeTab"],
  "content_scripts": [
    {
      "matches": ["<all_urls>"],
      "js": ["js/highlight-injector.js"],
      "css": ["styles/highlights.css"],
      "run_at": "document_idle"
    }
  ]
}
```

**为什么用 `activeTab` 而非 `<all_urls>` 的主权限？**

- 用户首次高亮时，动态申请 `activeTab` 权限
- 避免安装时就请求"读取所有网站数据"的惊悚感
- 符合 Chrome Web Store 的隐私最佳实践

## 四、关键功能详解

### 4.1 页面划线标注高亮系统（战略级功能）

这是 **连接"浏览"和"知识管理"的桥梁** ，是用户劳动投入最深的模块，也是最强的付费锁定。

#### 存储结构

```javascript
{
  id: "uuid",
  url: "https://...",
  domain: "github.com",
  title: "Page Title",
  
  // 四层定位信息
  range: {
    // L1: 精确 XPath
    startPath: "//div[@id='content']/p[3]",
    startOffset: 42,
    endPath: "//div[@id='content']/p[3]",
    endOffset: 128,
    
    // L2: CSS 选择器 + 文本指纹
    cssSelector: "article.content p:nth-child(3)",
    text: "高亮的原始文本（用于容错恢复）",
    contextBefore: "前文50字...",
    contextAfter: "...后文50字",
    
    // L3: 语义特征（用于相似度匹配）
    semanticHash: "base64-encoded-vector",
    
    // L4: 视觉坐标（快照叠加用）
    visualPosition: {
      xPercent: 0.15, yPercent: 0.23,
      widthPercent: 0.70, heightPercent: 0.03
    }
  },
  
  color: "yellow|green|blue|red",  // 不同颜色代表不同意图
  note: "用户添加的备注（Markdown）",
  tags: ["bugfix", "redis"],
  createdAt: timestamp,
  lastViewed: timestamp,
  snapshotRef: "snapshot-id",  // 关联快照
}
```

#### 四层容错恢复算法

| 层级 | 策略 | 触发时机 | 成功率目标 |
| --- | --- | --- | --- |
| **L1** | 精确 XPath 定位 | 页面加载时 | 60% |
| **L2** | CSS 选择器 + 文本指纹（编辑距离 < 15%） | L1 失败时 | 25% |
| **L3** | 段落语义相似度（TF-IDF / 本地 Embedding，余弦相似度 > 0.7） | 用户交互时异步触发（Web Worker） | 10% |
| **L4** | 快照坐标叠加（兜底） | L1-L3 全部失败 | 5% |

**恢复流程** ：

1. 页面加载 → 尝试 L1（同步，< 10ms）
2. L1 失败 → 延迟尝试 L2（异步，< 100ms）
3. L2 失败 → 用户打开高亮侧边栏时触发 L3（Web Worker，< 500ms）
4. L3 失败 → 显示"快照查看"入口，在 MHTML 上用绝对定位叠加高亮层

#### 与快照的联动

```markdown
用户高亮
    │
    ├──→ 内容脚本记录 Range + 视觉坐标
    │
    ├──→ 触发后台保存 MHTML 快照（首次高亮时，约 800KB/页）
    │
    ├──→ 高亮文本权重×2 进入全文倒排索引
    │
    └──→ 迷你工具栏弹出：🎨 换色 | 📝 加笔记 | 📌 加到 Workspace
```

#### 渲染性能策略

- **Intersection Observer** ：只渲染视口上下 200px 内的高亮
- **CSS Containment** ： `contain: layout style paint` 减少重排影响
- **事件委托** ：避免每个高亮单独绑定监听器
- **分批渲染** ： `requestIdleCallback` 每批 5 个，避免阻塞主线程
- **Shadow DOM / adoptedStyleSheets** ：绕过 CSP 限制

| 搜索结果返回 | < 100ms | IndexedDB 倒排索引 + Web Worker |
| 语义搜索 | < 500ms | 本地 Embedding，WebGPU 加速（transformers.js） |
| 高亮恢复率 | \> 90% | 四层容错算法 |
| 高亮渲染（50 处） | \> 55fps | Virtual Scroll + CSS Containment + 分批渲染 |
| 单页快照大小 | < 10MB | 压缩图片，排除视频/广告 iframe |
| 单用户存储上限 | 2GB | LRU 清理策略，分层归档 |

### 5.4 隐私与安全架构

```markdown
数据生命周期:
页面访问
    │
    ├──→ 内容脚本提取文本（本地）
    ├──→ 本地 IndexedDB 建立索引
    ├──→ 用户高亮 → 本地存储 + 本地快照
    │
    ▼
跨设备同步（Pro）
    │
    ├──→ 用户密码派生 AES-256-GCM 密钥
    ├──→ 数据在本地加密
    ├──→ 加密 blob 上传至同步服务器
    ├──→ 设备 B 下载 blob → 本地解密
    │
    └──→ 服务器无法解密，零知识架构
```

**隐私功能清单** ：

- ✅ 隐私模式（Incognito）历史自动排除
- ✅ 敏感网站黑名单：设置域名后历史不存储、不索引、不显示
- ✅ 一键紧急清除：立即清除插件内所有数据
- ✅ 可选密码保护：打开 side panel 需输入密码
- ✅ 区块链时间戳存证（律师场景）：关键页面哈希上链

## 十、总结：HistoryMind 的终极形态

> **HistoryMind 的终极形态不是一个"历史管理器"，而是一个"个人浏览智能中枢"。**
> 
> 它知道你昨天研究了 Chrome 插件（Continue Research），知道你三个月前高亮过一段 Redis 限流代码（语义搜索找回），知道你把 18 个页面存进了"论文写作"Workspace（一键恢复），知道你每天下午 3 点最容易分心刷社交媒体（生产力报告）。
> 
> 它从不把数据上传到任何服务器，但它比任何云端服务都更懂你——因为 **它记录的不是你访问了什么网址，而是你在互联网上思考过的每一个痕迹。**
